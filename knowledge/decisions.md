## Decisions

### 2026-03-08 — Initial project setup

**Status**: Accepted

**Context**: Starting a new project that needs a solid foundation.

**Decision**: Using uv with src layout, ruff + black for linting/formatting, pytest for testing, and MkDocs for documentation.

**Consequences**: Consistent project structure that follows Python best practices. All team members and AI assistants can rely on the same conventions.

---

### 2026-03-08 — Extension-based architecture for library-specific introspection

**Status**: Accepted

**Context**: Three projects (pyramid-client-builder, pyramid-mcp, pyramid-grpc) each implement their own Pyramid view introspection with significant code duplication. The complexity comes from different libraries (Cornice, pycornmarsh) decorating views in their own ways.

**Decision**: Use an extension/plugin architecture where the core discovers plain Pyramid routes/views, and extensions enrich the results with library-specific metadata. Extensions implement the `IntrospectionExtension` protocol and are auto-discovered from built-ins and entry points.

**Consequences**:
- New library support can be added without modifying core code.
- Third parties can register extensions via entry points.
- Extension ordering matters (pycornmarsh depends on Cornice) -- currently handled by built-in loading order.
- Consumer projects (pyramid-client-builder, pyramid-mcp, pyramid-grpc) can depend on this library instead of reimplementing introspection.

### 2026-03-08 — Route-centric data model (RouteInfo containing ViewInfo)

**Status**: Accepted

**Context**: pyramid-client-builder uses an endpoint-centric model (one EndpointInfo per route+method), while pyramid-mcp uses a route-centric model with nested view info. Both need to handle multiple HTTP methods per route.

**Decision**: Use a route-centric model where `RouteInfo` groups `ViewInfo` objects. Each ViewInfo represents one HTTP method handler with its own parameters, schemas, and permissions.

**Consequences**:
- Natural mapping to how Pyramid organizes routes and views.
- Consumers that need flat endpoint lists can easily flatten the structure.
- Path parameters are shared per route and copied to each view, avoiding duplication in the data model.

### 2026-03-08 — Validator location detection via closure inspection

**Status**: Accepted

**Context**: Cornice marshmallow validators (`marshmallow_body_validator`, `marshmallow_querystring_validator`) are generated by the same factory function `_generate_marshmallow_validator`. The location string is stored as a closure variable, not as an attribute or in the qualname. The previous approach (matching `__qualname__`) was brittle and version-dependent.

**Decision**: Detect parameter location by inspecting the validator's `__closure__` cells for known location strings ("body", "querystring", "path").

**Consequences**:
- More robust than qualname matching -- works across Cornice versions.
- Relies on CPython closure internals, but these are stable across Python 3.x.
- Falls back to "body" if no closure is found, matching the previous default.

### 2026-03-08 — Permission extraction from related introspectables

**Status**: Accepted

**Context**: Pyramid does not store permission values directly in view introspectables. Instead, permissions are stored in a separate "permissions" category and linked via the "related" field in the introspection item.

**Decision**: Extract permissions by traversing `view_item["related"]` to find introspectables with `category_name == "permissions"`, then reading the `value` key or `discriminator`.

**Consequences**:
- Correctly extracts permissions that the simpler `view_intr.get("permission")` approach misses.
- Requires passing the full view item (not just the introspectable) through the discovery pipeline.

### 2026-03-08 — Security type as a first-class ViewInfo field

**Status**: Accepted

**Context**: The authentication/security type (e.g. "bearer", "BearerAuth", "basic") was stored only in `view.extra["pcm_security"]` by the pycornmarsh extension. All three consumer projects (pyramid-mcp, pyramid-grpc, pyramid-client-builder) need this information, and it represents a core concern rather than extension-specific metadata.

**Decision**: Add `security: str | None = None` as a first-class field on `ViewInfo`, populated by the pycornmarsh extension from `pcm_security`. The value is also kept in `extra["pcm_security"]` for backward compatibility.

**Consequences**:
- Consumers access security type uniformly via `view.security` without knowing the predicate name.
- Aligns with how `permission` is already a first-class field for Pyramid's built-in authorization.
- Extensions that use different predicate names (e.g. `mcp_security`) can set the same `view.security` field.

### 2026-03-08 — Full MkDocs documentation site with mkdocstrings

**Status**: Accepted

**Context**: The docs site had only a minimal `index.md` with "API Reference: Coming soon." The README was comprehensive but the MkDocs site -- the canonical documentation home -- was nearly empty.

**Decision**: Build five documentation pages (landing, getting started, usage guide, extensions guide, API reference) using MkDocs Material with `mkdocstrings[python]` for auto-generated API docs from source docstrings.

**Consequences**:
- Users get a proper documentation site with navigation, search, and dark mode.
- API reference stays in sync with source code via mkdocstrings auto-generation.
- `mkdocstrings[python]` added as a dev dependency.
- Docs deploy on release via the existing CI workflow (`mkdocs gh-deploy`).

### 2026-03-08 — Lower minimum Python to 3.10 and add tox for multi-version testing

**Status**: Accepted

**Context**: The project required Python 3.12+, but the codebase uses no 3.11+ or 3.12+ syntax. All type hints (`str | None`, `list[X]`) are PEP 604/585 features available since Python 3.10. The overly aggressive floor excluded users on 3.10 and 3.11 without reason. Additionally, CI only tested against a single Python version.

**Decision**: Lower `requires-python` to `>=3.10` and add tox (with `tox-uv`) for testing across Python 3.10, 3.11, 3.12, and 3.13. CI now runs lint as a separate job and tests each Python version via a matrix strategy using tox.

**Consequences**:
- Broader audience: users on Python 3.10 and 3.11 can now use the library.
- Multi-version CI catches compatibility regressions early.
- `tox` and `tox-uv` added as dev dependencies.
- Developers can run `uv run tox` locally to test all versions before pushing.

### 2026-04-02 — Nested schema introspection on SchemaInfo (tree structure)

**Status**: Accepted

**Context**: The introspector captured top-level schema fields but dropped three important marshmallow properties: `allow_none`, `many` (on Nested fields), and nested schema references. When a schema like `PersonSchema` had `phones = Nested(PhoneSchema, many=True)`, the generator had no way to know it was a list of `PhoneSchema` objects, and `PhoneSchema` itself was never captured. This forced generators to fall back to `ma.fields.Dict()` instead of emitting proper `ma.fields.Nested(PhoneSchema)`.

**Decision**: (1) Add `allow_none`, `many`, and `nested_schema` to `SchemaFieldInfo`. (2) Add `nested_schemas: list[SchemaInfo]` to `SchemaInfo`, creating a tree that mirrors the marshmallow schema graph. (3) Recursively discover nested schemas in `_schema_to_schema_info` with cycle protection via a `_seen` set.

**Consequences**:
- Generators can emit accurate `Nested(SchemaClass, many=True)` and `List(Nested(SchemaClass))` field definitions.
- `allow_none=True` fields are correctly represented, preventing false `ValidationError` on null values.
- Nested schemas are self-contained within their parent `SchemaInfo` — consumers can flatten the tree with a simple recursive walk.
- Circular schema references (self-referencing schemas) are handled gracefully without infinite recursion.
